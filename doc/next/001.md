> **qdagent 不应该是“一个用 Marqdo 写出来的 Agent”。**
>
> 它应该是第一个真正证明 Marqdo 价值的 **AI-native Engineering Agent**：
>
> **它把一个代码仓库变成一个可执行、可检索、可验证、可演化的工程知识库，并利用这个知识库持续降低 AI 编程的重复劳动。**

> **普通 Agent 每次都在“重新理解代码”；qdagent 应该让 Agent 逐渐“不需要重新理解”。**

# 一、先重新定义 qdagent

我建议把 qdagent 的定位从：

> **General-purpose LLM Agent**

彻底改成：

> # **Engineering Knowledge Agent**
>
> 一个能够理解、执行、验证、记忆并逐渐编译大型软件工程知识的 AI Agent。

它的核心任务不是：

```text
用户 → LLM → 工具 → LLM → 答案
```

而应该是：

```text
                    ┌─────────────────────────┐
                    │      Engineering Repo   │
                    │                         │
                    │  Code / Docs / Tests    │
                    │  Decisions / Failures   │
                    │  Examples / APIs        │
                    └────────────┬────────────┘
                                 │
                         Knowledge Compiler
                                 │
                                 ▼
                    ┌─────────────────────────┐
                    │   Engineering Knowledge │
                    │                         │
                    │ Facts                    │
                    │ Capabilities             │
                    │ Constraints              │
                    │ Decisions                │
                    │ Patterns                 │
                    │ Failures                 │
                    │ Workflows                │
                    │ Dependencies             │
                    └────────────┬────────────┘
                                 │
                           Resolve / Reuse
                                 │
                                 ▼
┌──────────┐              ┌───────────────┐
│ User Task│─────────────▶│ qdagent       │
└──────────┘              │               │
                          │ Understand    │
                          │ Resolve       │
                          │ Reuse         │
                          │ Adapt         │
                          │ Create        │
                          │ Verify        │
                          └───────┬───────┘
                                  │
                                  ▼
                           Knowledge Update
                                  │
                                  ▼
                         `.mq.md` / OKF
```

这才是 **代码即文档 → 文档即知识库 → 知识库反过来指导代码生成** 的闭环。

# 二、我认为现在 qdagent 最大的问题

从你描述的现状，以及 Marqdo 自己已经锁定的新 Agent 设计来看，最关键的问题不是某一个模块写得不好，而是**抽象层错了**。

Marqdo 自己已经明确否定了：

> “黑盒对话循环 + 隐藏 prompt + TOOL 协议 + host history”

因为这种架构只是把 LangChain / CrewAI 一类 Agent 搬到了 Marqdo 里，并没有利用 Marqdo 的本质优势。Marqdo 的 Agent 设计文档已经明确指出这一点。([GitHub][2])

所以 qdagent 也绝对不能继续围绕：

```text
Planner
  ↓
Executor
  ↓
Tool
  ↓
Memory
  ↓
LLM
```

做增强。

因为这仍然是传统 Agent 的思维。

# 三、qdagent 应该有四个“真相”

这是我最希望你在 qdagent 1.4 / 2.0 中建立起来的东西。

传统 Agent 通常只有：

```text
Conversation History
```

qdagent 应该有：

```text
                qdagent Truth
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
     Program      Knowledge     Execution
        │            │            │
      `.mq.md`      OKF         Workbook
        │            │            │
        └────────────┼────────────┘
                     ▼
                  Evidence
```

具体来说：

## 1. Program Truth

代码是什么。

来源：

```text
*.mq.md
*.py
*.rs
*.ts
...
```

---

## 2. Knowledge Truth

这个系统**知道什么**。

例如：

```text
auth.verify_token
    ↓
Capability: JWT validation

Constraints:
- issuer must be validated
- expiry must be checked
- signing key rotation supported

Decision:
- authentication logic centralized in auth module

Failure:
- manual JWT parsing previously caused issuer validation bug
```

---

## 3. Execution Truth

Agent 实际做过什么。

不是：

```text
assistant:
...
```

而是：

```text
.marqdo/agent-runs/2026-09-28/...

Task
Plan
Step
Tool
Input
Output
Verification
Patch
Result
```

Marqdo 当前设计已经有 workbook、step、plan、writeback 这套基础，非常适合承担这个角色。([GitHub][2])

---

## 4. Evidence Truth

最重要但传统 Agent 很容易缺失。

例如：

```text
这个函数能处理 OAuth login
```

不能只是 LLM 说的。

应该能够追溯：

```text
Capability
    │
    ├── implemented_by → auth/login.mq.md
    ├── tested_by → tests/auth-login.mq.md
    ├── verified_by → run #184
    ├── derived_from → commit abc123
    └── last_verified → 2026-09-28
```

这样 qdagent 的“记忆”才不是 LLM 幻觉。

# 五、知识不应该只有 Module

现在 Marqdo 的 catalog 已经能够从 `.mq.md` 自动生成 YAML / Markdown catalog，这个方向是正确的：知识不是额外手工维护，而是从源文件派生。README 明确把 catalog 定义成从源码自动生成的知识包。([GitHub][1])

但是对于 qdagent 来说：

```text
Module
Function
Class
```

还远远不够。

应该至少有：

```text
Repository
    │
    ├── Module
    │     │
    │     ├── Type
    │     ├── Function
    │     └── API
    │
    ├── Capability
    │
    ├── Pattern
    │
    ├── Decision
    │
    ├── Constraint
    │
    ├── Failure
    │
    ├── Example
    │
    ├── Test
    │
    ├── Workflow
    │
    ├── Dependency
    │
    └── Migration
```

这会产生一个非常重要的区别：

### Function 是“代码存在什么”。

### Capability 是“系统已经能做什么”。

这是 qdagent 的核心。

举个非常重要的例子。

用户说：


```text

tested_by:
test.oauth.login

constraints:
- provider must support PKCE
- session must use existing auth session
- don't introduce second token store

- previous implementation used direct token persistence
```

然后：

```text

```

而不是：

```text
CREATE
```

# 七、所以 Agent 必须有一个新的核心协议

# 八、尤其要引入 REUSE / ADAPT / CREATE

这是我认为 qdagent 最值得做成产品级能力的地方。

每一个代码生成任务，在真正允许 LLM 写代码之前，都必须经历：

```text
              ┌─────────────┐
              │ User Task   │
              └──────┬──────┘
                     ▼
              Engineering Intent
                     │
                     ▼
              Knowledge Resolve
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
        REUSE      ADAPT      CREATE
```

### REUSE

已有能力直接满足。

### ADAPT

已有能力基本满足，需要修改/组合。

### CREATE

确实不存在。

# 十一、我甚至建议设计一个 Preflight

这是 qdagent 最重要的 Agent primitive 之一：

```text

```

输入：

```text
"implement OAuth login"
```

输出不是自然语言答案，而是一份 **Engineering Context Pack**：

```text

## Intent

Implement OAuth login using the existing authentication architecture.

## Existing Capabilities

- auth.oauth
- auth.session
- auth.token
- user.identity

## Recommended Reuse

auth.oauth.login

## Relevant APIs

auth.session.create
auth.token.verify

- PKCE required

## Tests

- tests/auth/oauth-login
- tests/auth/session

## Decision

Reuse existing OAuth infrastructure.

## Create Allowed

false
```

注意：

**这整个 Context Pack 本身应该是 `.mq.md`。**

这就非常 Marqdo 了。

# 十四、知识库不要只记录“成功经验”

这一点非常重要。

qdagent 的知识应该至少分成四大类：

## FACT

系统是什么。

```text
auth.oauth.login exists
```

## RULE

系统应该怎么做。

```text
OAuth login must use auth.session
```

## DECISION

为什么这么做。

```text
We centralized OAuth handling because ...
```

## FAILURE

以前哪里失败过。

```text
Do not manually persist provider tokens.
Previous attempt caused ...
```

实际上我认为：

> **FAILURE 是 AI Agent 最有价值的知识之一。**

因为传统 RAG 很容易告诉 Agent：

> “这里有一个 OAuth 实现。”

但它很难告诉 Agent：

> “这里有三个看起来都能用的方法，但其中两个已经失败过。”

# 二十五、生命周期

我建议 qdagent 的核心生命周期固定成：

```text
                    TASK
                      │
                      ▼
                 UNDERSTAND
                      │
                      ▼
                 PREFLIGHT
                      │
                      ▼
                  RESOLVE
                      │
             ┌────────┼────────┐
             ▼        ▼        ▼
           REUSE    ADAPT    CREATE
             │        │        │

                      │
                      ▼
                   VERIFY
                      │
                      ▼

                      │
                      ▼
```

其中：

### Understand

# 把 qdagent 彻底重构成 Marqdo 的第一个“工程知识智能体”

# qdagent 2.0 — Executable Engineering Knowledge Agent

核心理念只有一句：

而 qdagent 最终不应该只是“使用 Marqdo 写的 Agent”，它应该成为：

> **Marqdo Engineering Knowledge 的参考实现。**

# 3. 我建议把 qdagent 的中心对象从 Run 改成 Knowledge Artifact

这是这次重构最关键的一步。

现在：

```text
Run 是主对象
Knowledge 是 Run 的派生物
```

应该变成：

```text
Knowledge Artifact 是主对象
Run 是 Knowledge Artifact 的一种执行证据
```

整个模型：

```text
                    Knowledge Artifact
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
       Program          Knowledge        Evidence
          │                │                │
       .mq.md            OKF/EKC           Run
```

这样就真正和 Marqdo 的：

> 代码即文档、文档即知识库、知识即可执行

对齐了。

Marqdo 1.3.0 自己的 EKC 已经明确采用：

`.mq.md → EKC → Executable + Catalog L0–L4 + Graph + Context Pack`，

并把 Engineering First Information 定义成代码生成前需要的能力、约束、决策、失败经验和推荐复用。

# 4. qdagent 的核心应该变成 EFI

因此：

```text

    ↓

    ↓

```

而不是：

```text
User Task
    ↓
LLM
```

# 32. 例如：

```text

auth.verify_token exists.
```

```text
RULE

All API authentication must use auth.verify_token.
```

```text
Authentication logic is centralized to support key rotation.
```

```text
FAILURE

A previous implementation manually decoded JWT and bypassed issuer validation.
```

# 50. 另一个关键原则：不要让 Knowledge 全由 LLM 生成

# 51. 因此 Knowledge 的 evidence 很重要

每一条 Knowledge 至少应该能回答：

```text
What
Why
Source
Verified
Last verified

```

例如：

```yaml

status: stable

  - auth/security.mq.md
  - tests/auth/token.mq.md
verified:
  by: test
  at: 2026-09-28
---
```

这会非常接近 OKF 的 trust signal 思维，同时仍保留 Marqdo 自己的工程语义。Marqdo 对 OKF 的研究本身也已经把 `sources / generated / verified / status / stale_after` 作为重要方向。
