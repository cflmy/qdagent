我已经把你当前的 **qdagent `master`** 和 **Marqdo `main` / v1.3.0** 的设计重新对齐了一遍。现在 Marqdo 已经具备 EKC L0–L4、`find/reuse/duplicate/verify`、Engineering Preflight、Skill Compilation、Adaptive Routing、MCP 等能力；而 qdagent 当前最值得改的，不是继续增加功能，而是**把这些能力真正变成 qdagent 的核心执行链**。[qdagent 仓库](https://github.com/cflmy/qdagent?utm_source=chatgpt.com) [Marqdo 仓库](https://github.com/cflmy/marqdo?utm_source=chatgpt.com)

# 1. qdagent 2.0 的定位

不要把 qdagent 定义成：

> 一个带长期记忆的 AI Agent。

也不要把它定义成：

> 一个聊天 + RAG + MCP 工具。

最终定位应该是：

> **qdagent 是基于 Marqdo Engineering Knowledge 的 Executable Engineering Knowledge Agent。**

中文：

> **求道：可执行工程知识智能体。**

Marqdo 与 qdagent 的关系应该非常清晰：

```text
Marqdo
    ↓
Executable Knowledge Language
    ↓
Engineering Knowledge Compiler
    ↓
Executable Engineering Knowledge
    ↓
qdagent
    ↓
Engineering Knowledge Agent
```

因此：

```text
Marqdo = 知识如何成为程序

qdagent = Agent 如何利用并继续生产这种知识
```

# 3. 一个非常重要的原则

## qdagent 不应该拥有第二套 Agent Framework

这是当前架构最需要解决的问题。

目前存在两个思路：

```text
Marqdo ext/ai/agent
        +
qdagent Python Gateway Agent Loop
```

这是必须消灭的。

最终必须是：

```text
                         qdagent
                            │
              ┌─────────────┴─────────────┐
              │                           │
       Engineering Layer             Product Layer
              │                           │
        Preflight / EFI             Web / API / MCP
        Reuse / Record              Session / Auth
              │                     Streaming / Voice
              └─────────────┬─────────────┘
                            ↓
                    Marqdo Agent
                            ↓
                     Marqdo Runtime
```

换句话说：

> **Marqdo Agent 是唯一 Agent Runtime。**

qdagent 只负责：

```text
Engineering Knowledge
+
Product Surface
+
Persistence Policy
```

# 6. 最重要的 API：Preflight

qdagent 2.0 的 Killer Feature 应该是：

```bash
qdagent preflight "implement oauth login"
```

输出不是普通搜索结果。

而是：

```text
Engineering Preflight
────────────────────────────────

Task
  implement oauth login

Intent
  authentication / oauth / session

Existing Capabilities
  ✓ authentication
  ✓ token validation
  ✓ session creation
  ✓ user lookup

Relevant Modules
  auth/
  users/
  session/

Existing Functions
  auth.verify_token
  session.create
  users.find_by_email

Constraints
  OAuth provider must be verified
  JWT must not be parsed manually

Decisions
  ADR-007 authentication architecture

Failures
  auth/manual-jwt-parsing
  oauth/session-race-2025

Recommended
  REUSE auth.verify_token
  REUSE session.create
  ADAPT oauth.callback

Forbidden
  manual JWT parsing

Create Allowed
  yes

Reuse Budget
  2 candidates required
```

这是 qdagent 与普通 Coding Agent 最大的产品区别之一。

# 7. Preflight 的数据结构

建议统一成：

```yaml
---
type: Marqdo Engineering Context
version: 1
task_id: task-xxx
created_at: ...
---
```

正文：

```markdown
# Task

implement oauth login

# Intent

authentication
oauth
session

# Existing Capabilities

| Capability | Match | Confidence |
|---|---:|---:|
| authentication | exact | 0.98 |
| token validation | exact | 0.96 |
| session creation | exact | 0.94 |

# APIs

| Symbol | Module | Role |
|---|---|---|
| auth.verify_token | auth | token validation |
| session.create | session | session creation |

# Constraints

- JWT must not be parsed manually.
- OAuth provider must validate issuer.
- Existing session mechanism must be reused.

# Decisions

- ADR-007 defines authentication architecture.

# Failures

- manual JWT parsing caused issuer validation problems.
- OAuth callback previously created duplicate sessions.

# Recommended

- REUSE auth.verify_token
- REUSE session.create
- ADAPT oauth.callback

# Forbidden

- manual JWT parsing

# Create Allowed

true
```

这就是：

> **Context Pack**

但最关键的是：

> Context Pack 本身就是 `.mq.md`。

不是一个隐藏 JSON。

# 10. Capability 是核心对象

Function：

```text
auth.verify_token()
```

只是一个函数。

Capability：

```text
Token Validation
```

代表一个工程能力。

一个 Capability 可以：

```text
implemented_by
    ↓
auth.verify_token

implemented_by
    ↓
auth.verify_access_token
```

也可以：

```text

    ↓
test_auth_token

constrained_by
    ↓
ADR-007

failed_by
    ↓
manual-jwt-parsing

used_by
    ↓
oauth.callback
```

因此 UI 不应该只显示：

```text

```

而应该显示：

```text
Capability
────────────────────

Implemented By
  auth.verify_token

Used By
  oauth.callback

  test_auth_token

  ADR-007

  manual-jwt-parsing

  OAuth
```

这才是真正的 Engineering Knowledge Graph。

# 13. Negative Knowledge 必须是一等公民

这是我认为 qdagent 最值得强化的一点。

普通 RAG 主要保存：

```text
怎么做
```

qdagent 应该同时保存：

```text
为什么这么做
```

以及：

```text
什么绝对不要这么做
```

例如：

```markdown
# AntiPattern

## Manual JWT Parsing

不要直接解析 JWT payload 判断用户身份。

Reason:

- issuer 未验证
- expiry 可能被忽略
- key rotation 无法统一处理
- audit 信息缺失

Use instead:

auth.verify_token
```

然后 Preflight：

```text
Forbidden

manual JWT parsing

Reason:
existing failure:
manual-jwt-parsing
```

这会极大提高 qdagent 的长期价值。

# 14. REUSE / ADAPT / CREATE 必须成为硬门

不要只是 Prompt 里告诉 Agent：

> 尽量复用。

这不可靠。

应该成为控制流。

```text
                Task
                  ↓
               Preflight
                  ↓
        ┌─────────┼─────────┐
        ↓         ↓         ↓
      REUSE     ADAPT     CREATE
        │         │         │
        └─────────┴─────────┘
                  ↓
               Execute
```

---

# 15. REUSE

如果发现：

```text
existing capability
```

则：

```text
CREATE = false
```

除非 Agent 明确证明：

```text
existing capability cannot satisfy task
```

例如：

```text
Task:
implement password reset

Existing:
password_reset.start
password_reset.verify
password_reset.complete
```

Agent 不应该重新创建：

```text
password_reset_v2
```

---

# 16. ADAPT

如果已有能力接近：

```text
oauth.callback
```

但：

```text
provider = GitHub
```

可以：

```text
ADAPT existing capability
```

而不是：

```text
CREATE new independent implementation
```

---

# 17. CREATE

只有：

```yaml
create_allowed: true
```

之后，Agent 才允许创建新的能力。

因此：

```text
AI Coding Agent
```

变成：

```text
AI Engineering Agent
```

这是非常大的区别。

```text
4. 这是 Verification 吗？
```


```text

```

→ 不允许。

如果：

```text
Execution 没有 Evidence
```

→ 不允许 Promote。

# 95. 我建议你现在真正执行的第一步

不要先改几十个文件。

**先只完成一个垂直切片：**

```text
qdagent preflight
```

让：

```bash
qdagent preflight "implement oauth login"
```

真正能够调用 Marqdo 1.3.0：

```text
agent_eng_preflight
        ↓
EKC
        ↓
REUSE / ADAPT / CREATE
        ↓
Context Pack
        ↓
.marqdo/agent/contexts/task-xxx.mq.md
```

一旦这个切片成功，后面的：

```text
build
verify
record
learn
MCP
OpenAI
UI
```

都会围绕同一个核心自然展开。

而不是像现在一样，每个入口再造一套 memory / retrieval / prompt / run 逻辑。

**这就是我认为目前 qdagent 从“一个已经有很多功能的 Agent 原型”进入“真正能证明 Marqdo 价值的系统”的最短路径。**

有一点尤其值得强调：Marqdo 当前已经明确把 `agent.preflight`、`agent.eng_reuse`、`agent.eng_record` 和 EKC 放进官方 Agent 能力中，所以 qdagent **现在最不应该做的是重新实现一套工程知识系统**；它应该成为这些能力的第一个完整产品化验证场。[Marqdo Engineering Knowledge 设计](https://github.com/cflmy/marqdo/blob/main/doc/design/engineering-knowledge.md?utm_source=chatgpt.com) [Marqdo Agent 设计](https://github.com/cflmy/marqdo/blob/main/doc/design/ext-agent.md?utm_source=chatgpt.com)

而你当前 qdagent 的 `openai_v1_gateway.py` 确实把 retrieval、profile 注入、LLM 调用、Run 写入、organize 等职责集中在 Python Gateway 中；这正是下一阶段应该逐步拆掉的部分。[当前 qdagent OpenAI Gateway](https://github.com/cflmy/qdagent/blob/master/scripts/legacy/openai_v1_gateway.py?utm_source=chatgpt.com)

**所以，如果你的目标是“最快进入开发”，我建议下一步不要再继续讨论架构。直接进入实现：我可以基于上面的规格，进一步给你逐文件设计 qdagent 2.0 的实际 `.mq.md` 源码——第一批直接写出 `agent/qdagent.mq.md`、`knowledge/context.mq.md`、`knowledge/resolver.mq.md`、`execution/run.mq.md` 的完整实现骨架，以及明确哪些现有文件逐行迁移/删除。**
