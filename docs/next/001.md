我重新阅读了 `qdagent` 最新的 `master` 分支（提交 [`4fbbe1b`](https://github.com/cflmy/qdagent/commit/4fbbe1b87c9e6196c3cfd1ade0aac85eec6e8efa?utm_source=chatgpt.com)，2026 年 11 月 19 日），并对照了 Marqdo 2.9.1 的原生智能体、上下文和知识编译能力。

## **一、我的总体判断**

**你的直觉是有技术依据的：目前 qdagent 最大的问题不是功能不足，而是抽象层次错位。**

它已经具备真实的执行、独立测试、任务恢复、函数段并行、知识编译和受限插件能力，但这些能力没有组成一个边界清晰、容易扩展的智能体框架。现在更像是：

> 一个功能逐渐丰富、拥有大量安全约束的“Marqdo 文稿自动开发系统”，外围再接上聊天、办公、研究和知识管理。

而你真正想要的是：

> **以 Marqdo 为原生执行与知识基础，能够渐进发现、组合、验证、沉淀和复用 SKILL 的通用智能体系统。**

这两者的架构差异很大。

我不建议继续在现有 `ext/root-skill` 上添加更多 `runtime/`、`calls/`、`guides/` 文件。应该做一次有明确迁移边界的架构重组：**把通用智能体机制从具体任务工作流中抽离，让 SKILL 成为系统的主要组织单位，让知识编译成为能力发现与可信复用机制。**

这不意味着推翻现有代码。已有的执行、验证和恢复成果恰恰值得保留。最新提交记录还表明，仓库已记录使用同一 7B 模型连续通过完整交付、取消恢复和中途刷新三项真实浏览器测试。说明现有实现并非不可用；问题在于它不适合作为长期扩展的基础。

## **二、我认为现有架构有七个核心问题**

### **1. 根入口的位置和身份不清楚**

现在实际上存在两个容易让开发者误解的入口。

| 位置                                                                                                                                             | 实际角色      | 问题                        |
| ---------------------------------------------------------------------------------------------------------------------------------------------- | --------- | ------------------------- |
| [`index.mq.md`](https://github.com/cflmy/qdagent/blob/master/index.mq.md?utm_source=chatgpt.com)                                               | 旧站点与开发参考  | 位于项目根目录，看起来最权威，却不是生产智能体入口 |
| [`ext/root-skill/index.mq.md`](https://github.com/cflmy/qdagent/blob/master/ext/root-skill/index.mq.md?utm_source=chatgpt.com)                 | 当前生产入口    | 真正运行的智能体却被放在扩展库目录中        |
| [`ext/root-skill/runtime/index.mq.md`](https://github.com/cflmy/qdagent/blob/master/ext/root-skill/runtime/index.mq.md?utm_source=chatgpt.com) | 实际阶段调度    | 真正决定下一步运行什么               |
| [`ext/root-skill/state.mq.md`](https://github.com/cflmy/qdagent/blob/master/ext/root-skill/state.mq.md?utm_source=chatgpt.com)                 | 状态、确认和持久化 | 根状态与领域工作流紧密耦合             |

更关键的是，根入口里的“分解意图、路由函数、拆分并行”与真实运行路径之间存在抽象落差。

生产 Go 宿主调用的是 `run`，后者直接进入已有状态机。那三个看上去像根智能体核心能力的函数，并不是实际运行时必经的三个调度环节。

这会造成一种很奇怪的维护体验：

**表面上根 SKILL 很简单，实际上根智能体的真正逻辑散落在几十份其他文稿中。**

我的建议是让项目里只有一个明显的智能体入口，例如：

`agent/index.mq.md`

而 `ext/` 应当只代表可复用扩展和宿主适配能力。

### **2. 通用 Agent 与“自动开发 Marqdo 函数”的工作流混在一起**

这是最严重的架构问题。

目前 [`runtime/index.mq.md`](https://github.com/cflmy/qdagent/blob/master/ext/root-skill/runtime/index.mq.md?utm_source=chatgpt.com) 的核心流程大致是：

意图确认

框架设计和确认

独立测试 + 函数段实现

整合交付与验收

这是一套有价值的 **软件开发工作流**，甚至可以成为求道非常有特色的能力。

但它不适合作为所有任务的通用执行流程。

假设用户说：

“解释一下量子纠错码和表面码的区别。”

用户需要的可能是一次知识检索、几次必要核实以及回答，而不是首先创建一个工程方案、拆出函数段、冻结测试、实现文稿，然后验收。

如果用户说：

“读取三个数据文件，绘图后生成一份论文分析报告。”

这属于数据分析和文档生成工作流，也不应该强行套用软件开发角色。

**通用智能体负责决定应该调用什么工作流；工作流本身才决定有哪些步骤。**

这个边界必须重新建立。

### **3. 路由被五种固定工作方式限制住了**

我检查了 [`routing.mq.md`](https://github.com/cflmy/qdagent/blob/master/ext/root-skill/routing.mq.md?utm_source=chatgpt.com)。

目前真正的一级分类主要是：

`text / select / code / research / document`

但这些并不是真正的 SKILL 分类，更像是**编写函数的五种实现方式**。

例如 `research` 会映射到 `calls/implement-document.mq.md`，`code` 会映射到 `calls/implement.mq.md` 的某个函数。

这意味着未来加入量子电路优化、金融计算、网页自动化、科研实验控制时，根路由都得不断变复杂。

正确的扩展方式应该是：**新增一个能力包，不必修改根路由源码。**

这里需要重新审视以前“禁止能力注册表”的约束。

我仍然不赞成人工维护第二套工具定义，但支持由 Marqdo 编译器自动生成的、可重建的**能力索引**。它是 `.mq.md` 源码的投影，而不是另一份业务事实源。

### **4. 文稿的文字很多，但模块的责任不够单一**

我统计了最新仓库的文件树：

root-skill 文稿

# **53**

份 .mq.md

总体积

# **528**

约 KiB

runtime 子目录

# **20**

份文稿

注意，这不代表模型每轮读取了 528 KiB；现有系统已经能够按函数摘取上下文。

真正的问题是**维护复杂度**。

在 `runtime/index.mq.md`、`runtime/prompts.mq.md` 等文件中，有大量重复出现的授权、阶段、证据和失败处理叙述。不同文件反复解释系统级原则。

如果每个函数都需要重复描述全局行为，往往说明全局约束没有被有效抽象到一处。

Marqdo 的“代码即文档”，不是要求把相同的说明文字复制到每个函数里。

我建议以后严格区分三种文字：

| 文字类型           | 应放在哪里         |
| -------------- | ------------- |
| 全局运行与安全契约      | 一份内核开发契约      |
| 当前 SKILL 的领域规则 | 该 SKILL 的入口文稿 |
| 当前函数的行为与参数     | 该函数自己的文档段落    |

这样读者打开一份文稿，就能知道这个模块独有的职责，而不是先读几百字重复原则。

### **5. 小模型承担了过多语法生成任务**

这一点有真实数据支持。

最新的 [小模型测试记录](https://github.com/cflmy/qdagent/blob/master/docs/design/small-model-native-agent-rollout.md?utm_source=chatgpt.com) 显示，固定意图任务下：

| 模型                        | 成功到达 `waiting_user` | 结果                  |
| ------------------------- | ------------------- | ------------------- |
| Qwen2.5-0.5B-Instruct     | 0/3                 | 未能完成合法动作            |
| Qwen2.5-3B-Instruct       | 0/3                 | 经常出现调用与语法错误         |
| Qwen2.5-Coder-3B-Instruct | 3/3                 | 成功，但平均约 3.3 次真实模型尝试 |

记录中的每次尝试约消耗 19–27 KB 上下文数据。这个数字是上下文字节数，不是 token 数。

我认为这里暴露了一个非常深层的问题：

**为什么需要一个 0.5B 或 1B 模型生成完整 Marqdo 函数调用代码，才能表达“请选择研究 SKILL”？**

例如当前模型要学会：

```
Return *[保存意图](api.task(...))*.
```

但如果当前任务只是选择下一层能力，模型输出：

```
research
```

然后由 Marqdo 校验并调度，不是更容易成功吗？

上游 Marqdo 已经有 [`flow.choose`](https://github.com/cflmy/marqdo/blob/v2.9.1/ext/ai/flow.mq.md?utm_source=chatgpt.com)，支持固定候选选择、格式校验及有界修复。

我主张建立一条重要原则：

**小模型能只输出一个已注册选择时，就不要要求它生成程序。只有真正需要开发程序的 SKILL，才让模型编写 Marqdo 源码。**

这不会削弱 Marqdo 的地位。恰恰相反，是把控制权从概率模型移回了 Marqdo 的可验证执行系统。

### **6. 状态机、记忆和知识仍未形成清晰的层次**

现在已有 `state.mq.md`、`memory.mq.md`、工作簿、知识索引、执行收据和其他缓存。

这些各自都有必要，但开发者很容易搞混：

“到底什么才是可信事实？”

我建议明确三个概念：

**State（状态）**：权威的运行进度、确认、权限、依赖与版本，必须持久化且可恢复。

**Memory（记忆）**：从权威状态和必要知识提取出来的、给模型看的短文稿；是投影，不是新的权限事实源。

**Knowledge（知识）**：可长期复用的函数、契约、来源、测试和证明制品，不绑定某一次聊天。

它们的关系应该是：

**状态 State + 知识 Knowledge**

可信数据与长期制品

**构造当前决策所需上下文**

按函数、来源和预算裁剪

**小模型单步决策**

跨轮确实可以继续只向模型注入一份 `memory.mq.md`，但不应该强迫执行状态、审计、所有知识和证明都存进这一份文稿。

### **7. 通用编排和领域能力缺少明确扩展接口**

当前 `ext/knowledge/index.mq.md` 已经提供 `projections`、`compose_proof`、`replay_proof` 和 `proof_job` 等实际函数。也就是说，上游知识能力并非尚未接入。

但知识编译、证明执行、知识发布、用户身份和根状态仍然存在较多相互依赖。

新增领域能力需要理解很多内部文件。

我认为一个优秀的智能体框架应该满足这样的要求：

> 如果明天增加一个“量子科研 SKILL”，开发者应只需要了解该领域、Marqdo 标准接口和必要权限，而不必修改通用状态机、模型提示组装、根路由和前端业务分支。

这是判断架构是否真正具备扩展性的核心标准。

## **三、我推荐重新设计的架构：Marqdo-Native Capability Agent**

我不建议采用传统 LangChain 式 Agent，也不建议采用严格固定的树状 SKILL 调度器。

我推荐一个混合架构：

**以 Marqdo 函数为能力单元，以知识图谱为发现机制，以持久化工作流为执行机制，以独立证据为可信性基础。**

入口层

**Agent Root**

接收任务 · 发现候选 · 确认必要决策

能力与知识层

SKILL 能力索引

按需发现函数

Knowledge Graph

来源、版本和依赖

Contract & Proof

参数、效果和证据

Context Selector

精准提取上下文

Marqdo 原生执行层

flow / workflow

决策与检查点

subtask

任务依赖与并发

sandbox / effects

受控执行

Evidence

验证与收据

**领域 SKILL**

Chat · Research · Code · Office · Knowledge · Quantum · 自定义扩展

可信宿主：身份、文件、进程、资源、事件与权限

### **核心设计一：根 SKILL 应该几乎没有业务知识**

新根入口不应该了解 `text`、`code`、`research` 这类固定实现方式，也不应该知道 PPT 怎样生成。

它只需要完成三个逻辑动作：

**发现当前可用能力 → 判断是否需要用户澄清 → 选择或分发下一层工作。**

而且这些逻辑应尽量通过确定性函数完成。

模型只处理确定性代码无法解决的语义判断。

例如用户请求“比较三份研究论文并做一个 PPT”。

根并不需要规划论文怎么阅读、报告怎么写。它只需生成经过校验的任务意图，然后分配给研究和办公 SKILL。

真正的细分由领域 SKILL 完成。

### **核心设计二：SKILL 应该是独立能力包，而不是角色提示词**

我建议将 SKILL 看作一个可安装、可引用、可验证、可组合的**知识能力包**。

最简单的 SKILL 只有一个 `## run` 函数也可以。

复杂 SKILL 可以提供自己的规划、执行、验证和恢复函数，但不能要求所有 SKILL 一律实现同一套庞大的生命周期。

一个能力最少要让系统知道它解决什么问题、输入输出是什么、有什么效果要求、来源版本是什么，以及如何调用。

这些信息优先从 `.mq.md` 文档元信息、函数签名、契约和编译投影中取得。

不必维护另一份重复的 JSON 工具 Schema。

例如：

```
skills/research/
  index.mq.md          ← 领域入口
  search.mq.md         ← 搜索能力
  read.mq.md           ← 资料读取
  synthesize.mq.md     ← 综合分析
  verify.mq.md         ← 来源核验
```

根智能体只能看到 Research 这一个候选能力，以及一句摘要。

进入 Research 后，才知道它有 search、read、synthesize 等函数。

这就是你想实现的**逐层展开，而不是一次加载所有上下文**。

### **核心设计三：通过知识编译器发现能力，而非手工路由**

这是 Marqdo 最有特色、也最值得投入的地方。

传统 Agent 通常需要手写工具清单、描述文字和 Schema。

但 Marqdo 本身就有可寻址函数、语义符号、依赖图、契约、知识索引和证据结构。

因此可以设计这样的流程：

```
SKILL 源文稿
      ↓
Marqdo 官方解析和知识编译
      ↓
可重建能力索引
      ↓
根据目标检索候选函数
      ↓
宿主过滤未安装或无权限的能力
      ↓
给小模型 2～5 个候选摘要
      ↓
校验选择并进入 SKILL
```

这里的“可重建能力索引”是我建议建设的 qdagent 层接口，并不是宣称现有编译器已经完整支持这样的 SKILL 注册和匹配。

它应该尽量建立在上游现有的 `knowledge find`、`reuse`、`preflight`、符号索引和函数元信息上。

最终，**添加 SKILL 的动作就是添加一个 Marqdo 能力包，而不是去修改根智能体的条件判断。**

### **核心设计四：必须区分“能力选择”和“能力实现”**

我建议严格区分两类模型调用：

| 类别    | 模型应该输出                  | 适用任务             |
| ----- | ----------------------- | ---------------- |
| 控制性决策 | 一个候选 ID 或极短的结构化选择       | 路由、继续、停止、选择验证方式  |
| 生成性工作 | 当前函数的 Marqdo 源码、文档内容或参数 | 编写算法、研究报告、生成业务知识 |

对于第一类，即使模型只有 0.5B～1B，也不应强迫它生成复杂 Marqdo 语法。

对于第二类，允许更强的模型和更大的上下文，但限定在当前 SKILL 内。

这是充分利用 Marqdo 特性的关键：**模型负责决策和生成，Marqdo 负责结构、执行和验证。**

### **核心设计五：工作流应该是一等公民，但不应成为整个 Agent**

软件开发是一个工作流。

科研实验是一个工作流。

论文写作、采购、旅行规划也可以各有工作流。

Marqdo 已经具有 `ext/ai/workflow.mq.md`，提供持久化步骤、查询、提交和有限恢复。通用工作流应该优先复用这些原生能力，不再从头构造独立 Agent Loop。

不过其当前接口仍有步骤种类、输入选项和自动执行效果方面的边界，不能直接声称它已经支持任意动态 DAG。

我会设计成：

工作流是**可选的能力组合结构**。简单任务可以直接调用一个函数，复杂任务才使用持久计划、任务依赖和并发调度。

这样不会为了回答一个简单问题而先创建完整工程项目。

## **四、我会怎样重新组织整个仓库**

这是我推荐的目标目录，不是已经完成的迁移。

**qdagent/**

```

qdagent/
├── agent/
│   ├── index.mq.md          # 唯一智能体入口
│   ├── dispatch.mq.md       # 能力发现与分派
│   ├── context.mq.md        # 当前函数上下文
│   ├── session.mq.md        # 会话与持久状态
│   └── evidence.mq.md       # 执行证据聚合
│
├── skills/
│   ├── chat/
│   │   └── index.mq.md
│   ├── research/
│   │   ├── index.mq.md
│   │   └── ...
│   ├── code/
│   │   └── index.mq.md
│   ├── office/
│   │   └── index.mq.md
│   ├── knowledge/
│   │   └── index.mq.md
│   ├── quantum/
│   │   └── index.mq.md
│   └── dev/
│       └── index.mq.md
│
├── workflows/
│   ├── software-development/
│   ├── research-report/
│   └── knowledge-compilation/
│
├── ext/
│   └── qdagent/             # 产品原生 ABI 适配
│
├── server/                  # 可信 Go 宿主
├── worker/                  # 模型传输
├── frontend/                # 工作台
├── docs/                    # 架构与开发文档
└── tests/
  
```

这个目录结构有几个关键区别。

`agent/` 是产品的通用智能体运行层，不是第三方扩展库。它应保持足够薄，只处理能力发现、上下文选择、任务调度和证据整合，并复用 Marqdo 上游的原生实现。

`skills/` 是用户真正可扩展的领域能力，新增 SKILL 应尽量只增加一个目录及其所需依赖。

`workflows/` 是可复用的多阶段执行流程。当前成熟的“意图 → 框架 → 独立测试 → 实现 → 交付”应该成为 `software-development` 工作流，而不是被删除。

`ext/` 则继续放 Marqdo 扩展、特定原生 ABI 与必要系统适配，不负责定义所有智能体的业务行为。

这也意味着不必再使用 `root-skill` 这个含义模糊的名字。根就是 `agent/index.mq.md`。

## **五、我还想推翻两条之前过于绝对的设计约束**

### **第一条：不是所有用户输入都必须先确认一次**

此前我们设计的根 SKILL 要求每个非空输入都进行一次用户确认。

这对于工程任务很有用，因为它能冻结可交付范围，但对于一般智能体交互过于严格。

例如用户问“什么是量子傅里叶变换”，再问他选择哪一种理解方案，没有太大必要。

新的原则应该是：

**意图不明确时澄清；涉及外部副作用、重要成本或改变用户资源时确认；已经明确的低风险只读任务可以直接执行。**

这可以同时减少用户交互次数和模型推理成本。

### **第二条：不是所有任务都要生成 Marqdo 新代码**

这是另一个重要转变。

Marqdo 的价值不在于让模型每次都重新写代码。

恰恰相反，**已有代码、知识和已验证能力能够直接调用**，才是这种语言最大的价值。

一个成熟的求道智能体应该优先采取：

**用户任务**

**查找已存在的知识与可执行函数**

**有可信能力**

核验版本与权限后复用

**不存在合适能力**

进入开发 SKILL 创建与验证

**执行 → 验证 → 必要时沉淀知识**

这条闭环比单纯研究如何让小模型生成更好的 Marqdo 代码重要得多。

但也不能机械地要求所有任务都先做昂贵的全库检索。对于明确选定的函数，直接核验并调用即可；对于未知需求，才利用知识编译进行能力发现。

## **六、重构优先级：我建议先做一条真实纵向切片**

不建议一上来把 53 份 root-skill 文稿全部移动，或者一次性重写完整状态机。那会丢失已有的真实验收成果。

我推荐按照下面的顺序迁移：

1\. **建立新&#x20;**`agent/index.mq.md`**&#x20;和统一能力包契约。** 从旧根目录分离产品入口、通用执行和领域工作流，保留旧入口兼容层。首先保证一个简单只读 SKILL 能在不修改根源码的情况下安装、发现和执行。

2\. **让小模型只输出候选选择。** 用 Marqdo 的 `flow.choose`、真实能力索引和许可校验完成一级路由。用目前测试失败的 0.5B、3B-Instruct 重新比较，不必一开始让它们生成函数调用。

3\. **将原根流程迁移为&#x20;**`workflows/software-development/`**。** 保留已有的版本确认、函数段冻结、独立测试、并发和真实交付机制。新根只是调用这一工作流，不需要了解其四个阶段。

4\. **实现 SKILL 按需发现与知识复用。** 将官方知识编译的符号、接口、来源和证据接入能力索引。每次只给模型最相关的少量候选，不重建一套手工工具目录。

5\. **扩展两个真正不同的领域 SKILL。** 我建议用 `chat` 和 `research` 作为第一批：前者验证简单任务不需要完整工程流程，后者验证多步检索、外部证据和必要时并发。再用 `quantum` 验证形式化知识、专业函数和科研实验边界。

6\. **最后删除兼容层与重复文档。** 等到功能、真实浏览器测试、恢复和小模型对照测试都通过，再逐步移动或移除 `ext/root-skill`、旧 `index.mq.md` 及重复的指令段落。

### **验收不应该只看“能不能运行”**

新的架构至少应该达到这样的结果：

| 指标         | 我建议的验收目标                  |
| ---------- | ------------------------- |
| 增加领域 SKILL | 不修改根调度代码                  |
| 根模型可见上下文   | 以约 1–2K tokens 为首选目标，真实计量 |
| 普通只读问题     | 无须创建软件开发工作簿               |
| 能力选择       | 模型输出一个候选 ID 即可            |
| 复用已有函数     | 不重新生成相同代码                 |
| 源码或契约变化    | 失效证据能够传播                  |
| 多任务并发      | 依据真实依赖和效果权限               |
| 小模型效果      | 同任务对照测量成功率、token 和调用次数    |

这些是设计验收目标，不是对尚未实现的新架构的性能承诺。

## **七、我认为 Marqdo 智能体真正有机会形成的原创范式**

回到更根本的问题：

**为什么一定要用 Marqdo 构建求道智能体？**

如果只是为了让模型调用工具、分解任务、维护状态，传统 Agent 框架也能做到。

Marqdo 应该发挥的是另一种能力：

**一个函数同时拥有可读描述、可执行逻辑、知识身份、来源依赖、验证证据和复用接口。**

这意味着未来智能体不是围绕聊天历史运行，而是围绕不断积累的**可信知识制品**运行。

模型在其中更像决策与开发组件，而不是系统的唯一控制核心。

我设想的成熟形态是：

用户提出目标，智能体先判断是否存在可复用知识；已有可靠能力就直接完成，缺少能力才调用合适的开发流程。新能力通过真实测试、必要的证明与用户验收后沉淀为 `.mq.md`，以后其他任务按符号和契约调用，不再重复生成和推理。

这样的系统具有一种传统提示词驱动 Agent 很难自然获得的特性：

**随着可信知识的积累，重复任务对模型的依赖应该逐渐下降，而不是永远需要模型重新理解和规划。**

这是我认为最值得成为求道长期技术主线的方向。

## **最终架构取舍**

我比较三种可行方案：

| 方案                             | 优点                | 主要问题               |
| ------------------------------ | ----------------- | ------------------ |
| 严格层级 SKILL 树                   | 简单、上下文小、容易控制      | 容易形成固定路由；跨领域能力难组合  |
| 纯动态 Agent 规划器                  | 非常灵活、适合未知任务       | 对小模型依赖大，容易重复规划和膨胀  |
| **Marqdo 能力图 + 薄调度层 + 可组合工作流** | 兼顾扩展、复用、验证和小模型稳定性 | 需要建立真正可靠的能力索引与调用契约 |

我明确推荐第三种。

并且最关键的不是重写根 SKILL，而是重新划分系统的三个核心问题：

**“有什么能力”交给 Marqdo 知识编译和能力索引。**

**“当前应该用什么能力”交给小模型与确定性调度。**

**“怎样安全完成任务”交给 Marqdo 原生执行、工作流和验证系统。**

只要这三个职责真正分开，目录组织、SKILL 扩展、状态维护以及模型上下文缩减都会自然变得清晰。

我认为这是比继续打磨现在的 `root-skill` 更值得投入的一次重构，也更接近你希望 Marqdo 实现的“代码即文档，文档即知识库，知识即可执行”。
