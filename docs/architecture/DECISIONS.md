# 求道架构决策：上下文主权与 Marqdo 自主执行

> 2026-11-19 设计目标。完整规范见 [CONTEXT_SOVEREIGNTY.md](CONTEXT_SOVEREIGNTY.md)。此文替代此前“三份内容是不可突破上限”的决策。

## 起点不是上限

最初的三份信息（用户输入、记忆文档、当前 Marqdo 文稿）是合理的**默认最小启动集合**。但真实科研智能体在任务进行中会需要新信息。如果限制它永远不能访问额外函数、声明、证明、实验结果或来源，就无法发挥 Marqdo 的知识可寻址性。

因此，模型能够**主动提出上下文需求**，Marqdo 的上下文函数负责读取、扩展、引用、压缩和释放。对于模型不需要的信息，框架不能“好心地”预加载它。对于模型确实需要的信息，也不能由框架的固定三源规则禁止它获取。

## 为什么必须由 Marqdo 而不是外部 Agent 框架负责？

上下文决定是**认知行为**：阅读哪段源代码、验证哪个声明、调用什么函数、是否保留一个实验结论，本来就是智能体在执行的工作。如果 Go/Python/Rust 固定拼好消息，这些选择与执行失去统一语义，Marqdo 退化成工具调用格式。

将上下文管理写为 Marqdo 的可调用函数，可以保持代码即文档、可寻址引用、可复用知识制品、明确控制流、增量执行、来源校验和未来证明之间的连续性。外部宿主只实现它不能安全实现的能力：身份、OS、隔离、额度、资源权限、网络传输。

## 六个架构决定

| 决策 | 理由 |
|---|---|
| 默认极小启动，主动扩展 | 降低默认开销，同时避免固定三源天花板 |
| 语义作用域优先于大文本拼接 | Marqdo 函数/锚点/知识图本来可寻址 |
| 工作集由 Marqdo 文稿控制 | 上下文控制与实际执行同一语义体系 |
| 运行权限与认知上下文分离 | 自主阅读不意味着可以读取秘密或执行写入 |
| 暂态阅读与长期记忆分离 | 防止未经验证的模型解释污染知识库 |
| 引用与摘要、证据与失效绑定 | 便于更新代码、重放任务、精确纠错与形式证明 |

## 关于模型调用接口

目标不是 `model.ask(prompt=大量拼接内容)`，也不是 `model.ask()` 永远只能拿固定三段。目标是**由当前 Marqdo 文稿管理的工作集**：模型发起局部上下文选择请求 → Marqdo 校验读取 → 来源片段进入下一次模型调用。宿主只发送它收到的可审计工作集，不自行塞入第四段。

与其设计一个携带所有内容的 `context` 大字典，不如为 Marqdo 定义 `context.read(ref)`、`context.pin(ref)`、`context.release(ref)` 等明确的可组合能力。这里的 context 指的是模型可读知识作用域，而不是可信宿主身份参数。

## 优先复用 Marqdo 的能力

Marqdo 已有 `ext/ai/context.scope`、`ext/ai/flow`、`ext/ai/workflow`、可寻址知识与知识证明相关模块。应组合/扩展这些能力；不要复制其源解析器，也不要默认使用 `ext/ai/agent.build_step_context` 那套多段 Prompt 拼接路径。

## 诚实的实现状态

本设计仅规定期望的架构。实验分支目前的三源固定传输和无 context 接口并未实现本设计所需的动态工作集。这需要后续独立开发。本轮不进行测试和运行链路改造。
